# GCS Loop 离线包制作提示词

把下面整段内容交给负责制作离线包的现场人员或 Codex。根据当次需求填写方括号；没有要求携带业务数据时填“否”。

---

请基于当前服务器上已经完成部署和业务验证的 `gcs-loop`，制作一套可以带到无互联网现场直接安装的离线部署包。

当前服务器角色：[230 x86 主发布服务器 / 43 或 44 ARM 适配服务器]

项目目录：[例如 `/gcs-loop`]

离线交付目录：[项目根目录下的 `offline/`]

是否携带当前服务器业务数据：[是 / 否]

请遵守以下要求：

1. 先检查 Git 分支、提交、工作区、`uname -m`、Docker/Compose 版本、最终 Compose 配置、实际运行镜像和容器健康状态。以当前服务器已经验证的架构与产物为准。x86 服务器只制作 AMD64 包，ARM 服务器只制作 ARM64 包，不混用镜像。
2. 本次离线打包不重新编译代码。若镜像或程序尚未完成对应架构适配，明确指出缺失项并停止打包，不要临时用其他架构镜像替代。
3. 最终交付物是项目根目录下完整、自包含的 `offline/` 目录，现场只带走这个目录。将干净、与镜像版本一致的完整 GCS Loop 运行文件放入 `offline/runtime/`，排除 `.git`、日志、缓存、临时文件、中间产物、旧备份和嵌套的 `offline/`。
4. 将当前 Compose 实际需要的全部运行镜像通过一次 `docker save` 导出为一个 gzip 压缩文件，放在项目的 `offline/` 目录。不要把镜像提交到 Git，也不要要求现场联网构建或拉取。
5. 如果要求携带全部数据，在一致性停机窗口内备份 Compose 使用的全部 named volume，包括 Redis、MySQL、ClickHouse、MinIO、RocketMQ、Nginx 资源及两个 FaaS 工作卷；完成后恢复源服务器服务并验证健康。如果不要求数据，只制作可初始化空白环境的包。
6. 不复制 `/var/lib/docker`，不假设 Docker `data-root` 位于任何固定目录。现场数据必须由 Docker named volume 管理，备份和恢复通过 Docker volume 挂载完成。
7. `offline` 复制到任意绝对路径都必须能启动。现场脚本只能根据自身目录使用 `offline/runtime/`，不能回头依赖源服务器外层源码，也不能写死 `/gcs-loop`、`/root`、`/opt` 或其他源服务器路径。
8. 提供 `offline/site.env.example`，以制作服务器当前已经验证的公开访问 URL 和端口作为例子，并说明现场地址不同时需要修改。`offline/runtime/` 中的模型配置默认完整沿用制作服务器的已验证配置；只有现场无法访问相同 Endpoint，或模型名称、API Key 不同时才由现场修改。不要在 README、清单或命令输出中展示凭据明文。
9. 离线启动只能执行 `docker load` 和 `docker compose up --pull never`，不得触发源码构建、在线下载或镜像仓库访问。提供启动、停止、状态、日志和验收命令。
10. 验收至少检查：所有镜像架构正确；10 个常驻容器健康；4 个初始化容器退出码为 0；Nginx 到后端 API 的网关链路正常；外部 Web/API 地址可访问；如携带数据，再抽查 MySQL、Redis、ClickHouse 和 MinIO 数据。
11. 生成清单，记录源码提交、架构、镜像标签/Image ID/大小、是否包含数据和归档文件大小。不需要生成 SHA 校验文件。
12. 最终只把脚本、模板和文档提交 PR。确认 PR 与 `main` 无冲突后合并；生成的 `runtime/`、镜像包、数据包和清单只留在服务器的 `offline/`，不提交 Git。

项目已有 `offline/manage.sh` 时优先复用并检查它，不另写一套重复脚本。完成后报告自包含 `offline/` 的路径和总大小、包含的镜像和数据卷、源服务器服务恢复情况、实际恢复测试结果和现场需要填写的配置。
